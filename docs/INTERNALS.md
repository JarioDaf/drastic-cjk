# 注入原理与逆向笔记

这份文档解释 `src/` 里的代码为什么长这样，以及当初是怎么把这些地址找出来的。
如果你要改注入方式或适配新版本，先读这里。

---

## 1. 总体思路

本文说的"原版"特指 **Anbernic RG DS（安伯尼克双屏掌机）** 上 **ROCKNIX RK3566
20261001** 系统里的 `drastic`（ELF64 AArch64 PIE，1 411 544 B / md5 `3e5a8b42…`）
—— 从镜像 `ROCKNIX-RK3566.aarch64-20261001-Specific.img.gz` 中提取、未经修改。
下面所有地址都是针对这一份写的；据此产生的补丁版已在 RG DS 真机上验证通过。

目标：给一个**已 stripped 的 AArch64 PIE 可执行文件**加中文渲染能力，同时满足：

- 不能破坏 .bss —— 内核只按 ELF 头算一次匿名映射，`elf_bss`/`elf_brk` 动了就崩
- 不能产生 **W+X** 段
- 不能依赖重定位 —— PIE 的注入段没有任何东西会去修它
- 原版代码尽量不动 —— 最好只有函数入口那 4 个字节

做法：**回收一个用不上的程序头**，把它改写成新的 `PT_LOAD`，塞进原版两个
`PT_LOAD` 之间的地址空洞里。

```
原版地址空间
  0x000000 ┌──────────────────────┐ PT_LOAD  R-X  (代码, 到 0x14c800)
  0x14c800 ├──────────────────────┤
           │   ~64 KB 空洞        │   ← 注入段放这里 (0x150000, 9747 B)
  0x15d1f8 ├──────────────────────┤ PT_LOAD  RW   (.data / .bss)
  0x169000 │  .bss (匿名, 到 0x3f32240)
  0x3f32240└──────────────────────┘ elf_brk
```

注入段**严格低于 .bss**，所以 `max(vaddr+filesz)` 和 `max(vaddr+memsz)` 都不变，
内核看到的 bss 映射和原版**逐位相同**。

## 2. 为什么是 `PT_NOTE`

原版有个 `PT_NOTE` 段，但实际上没有可用的 note 数据（stripped，且内核不读它）。
它正好可以原地改写成 `PT_LOAD`：

```python
struct.pack_into("<IIQQQQQQ", out, ephoff + note_idx * 56,
                 1, 5, SEG_OFF, SEG_VA, SEG_VA, filesz, filesz, SEG_ALIGN)
#                │  │     │        │        │       │        │       └ p_align
#                │  │     │        │        │       │        └ p_memsz
#                │  │     │        │        │       └ p_filesz
#                │  │     │        │        └ p_paddr
#                │  │     │        └ p_vaddr
#                │  │     └ p_offset
#                │  └ p_flags = 5 (R-X)
#                └ p_type = 1 (PT_LOAD)
```

`p_align = 0x10000`，同时满足 4K / 16K / 64K 页内核的一致性要求
（`p_vaddr ≡ p_offset (mod p_align)` 也成立：0x150000 ≡ 0x160000）。

## 3. 必须守住的不变量

`patch.py` 里有十几条断言，全是踩过坑之后加的。核心是这几条：

```python
assert elf_bss(ph2) == elf_bss(hdr)      # = 0x1681a0
assert elf_brk(ph2) == elf_brk(hdr)      # = 0x3f32240
assert not (flags == 3)                  # 不许出现 W+X
assert SEG_VA + filesz <= VENDOR_BSS_START
assert (SEG_VA - SEG_OFF) % SEG_ALIGN == 0
```

还有一条**数据层**的：

```python
assert not _bad   # 镜像里不许出现落在注入段内 or 指向宿主地址的 8 字节值
```

这条是早期版本崩溃的根因。注入段是 PIE 的一个 `PT_LOAD`，但**没有任何东西给它做
重定位** —— 里面存着 `0x151b78`、`0x87f00` 这样的绝对指针，在设备上就是悬空地址。
Unicorn harness 把模块加载在 VA 0，那些指针**碰巧**是合法的，所以本地测试全绿，
真机一呼菜单就崩。修法是：只允许数组和 PC 相对引用，禁止指针表。

## 4. 两个钩子

只改两个函数的第一条指令，改成 `b`：

| 地址 | 原函数 | 作用 |
|---|---|---|
| `0x87f00` | `draw_text(s, fg, bg, x, y)` | 所有文本绘制 |
| `0x88430` | `fill_rect(color, x, y, w, h)` | 所有矩形填充（高亮框、光标、色块） |

```
入口 0x87f00:  b cjk_entry          (原 prologue: sub sp,sp,#0x50)
resume 0x87f04: 原函数体从这里继续
```

`entry.S` 里的桩：把参数和 `x30` 存到栈上 → 调 `cjk_draw()` → 恢复参数 →
如果返回 0（没接管）就补回被覆盖的那条 `sub sp,sp,#0x50` 再跳回 `__resume`。

**为什么要用 `x30`**：`draw_text` 的调用点是从 `bl` 的返回地址拿的，也就是
`draw_text` 入口处的 `x30`。注入层靠它区分"这一笔是谁画的"，这是整个菜单重构的
基础。代价是 `entry.S` 必须把 `x30` 提前压栈。

`cjk_rect` 的桩多存了一个 `a[6] = LR`：色块那一对 `fill_rect` 靠 **LR 指纹**
（外框唯一的 `bl` 落在 `0x799f0`）来识别。详见第 7 节。

同一段里还用 `adrp/add` 从 `__font_slot`(0x167668) 反推出**模块基址**，
再传给 C 代码 —— 这是注入层唯一需要运行时基址的地方。

## 5. 字库 blob

8 KB 的代码槽塞不下 900 KB 位图，所以字库**不参与链接**，是在文件 `0x170000`
处追加的一段裸数据，**故意不挂任何程序头**，运行时用 `mmap(/proc/self/exe,
offset=0x170000)` 读进来。

每个字库分节 8 字节头 + 8837 个字形 × N 行 u16：

| 分节 | 尺寸 | 内容 |
|---|---|---|
| cjk15 | 265 118 | 8 + 15×8837×2 |
| cjk10 | 176 748 | 8 + 10×8837×2 |
| cjk8 | 141 400 | 8 + 8×8837×2 |
| cjk16 | 282 792 | 8 + 16×8837×2 |
| uni_tab | 29 780 | 7445 个 u32，`(unicode<<16)\|gb_slot`，升序可二分 |
| 合计 | **895 838** | |

行按 u16 打包，**bit15 = 最左像素**。

注意：`cjk.c` 用编译期常量 `SZ15/SZ10/SZ8/SZ16` 定位各分节，**不读那 8 字节头**。
所以 `font_15/10/8.bin` 的头里是字形数量（8837）而不是尺寸 —— 历史遗留，
但改它会破坏可复现性，别动。

字库只作为**字形数据源**：渲染时把某一行字形拷到栈上的临时字体里，再把临时字体
指给宿主的 `font` 槽。宿主原生的 8×8 字模（`0x162e58`）则被原样读取、
**逐像素放大 2 倍**后装进同一个临时字体，所以中英混排的基线和字号是统一的。

## 6. 可写状态放哪

注入段是 R-X，**没有可写数据**。需要跨调用保存的状态（blob 指针、加载失败标志）
放在**原版 RW 段里一段没人用的零填充区**：

```
0x1681a0  .data 结束
0x168e00  ← 注入层的 state_t (魔数 "KJC1")
0x169000  .bss 开始
```

选 `0x168e00` 是因为它**超过了文件末尾**（`0x1589d8`），所以那部分页面尾部
一定是零，不会被原版数据污染。

## 7. 菜单引擎

原版菜单是靠一组"行渲染器"函数各自硬编码坐标画出来的。注入层不改它们，
而是在 `draw_text` 入口**按调用点 + 页面**重新决定每一笔文字画在哪。

### 调用点（模块相对地址）

```
S_LBL     0x79858   rowGen: 行标签
S_VAL     0x7987c   rowGen: 数值列
S_EDT_L   0x79fc0   0x79f40: 固件编辑器行标签（选中态）
S_EDT_0L  0x7a164   同上，未选中态
S_EDT_0V  0x7a188   同上，未选中态的字段值
S_DISP1   0x7d7a8   选项/视频页分发器
S_DISP2   0x7fdc0   主菜单分发器
...
```

`S_IS_LABEL(s)` 宏判断"这一笔是不是行标签"，只有标签才需要查行表定位。

### 页面与行表

```c
static const page_t PAGES[] = {
    /* 0 MAIN  */ { 272, 20, 344, 784,   0,   0,   0, 0xFFFF,  0 },
    /* 1 FIRM  */ {  56, 36, 256, 400, 560,   0, 400, 0xFFFF,  0 },
    /* 2 KEYSX */ {  40, 17, 216, 384, 544, 720,   0,     20, 10 },
    /* 3 OPT   */ {  56, 28, 256, 408, 560,   0,   0, 0xFFFF,  0 },
    /* 4 VIDEO */ {  48, 26, 256, 408, 560,   0,   0, 0xFFFF,  0 },
    /* 5 KEYS  */ {  40, 17, 216, 384, 544, 720,   0,     19, 10 },
};
```

行表 97 行，每行 `(标签在字符串表里的偏移, 宿主选的 y, page, row)`。

**两个坑**：

1. **"配置按键"和"额外按键"是两个不同页面**，但共用同一段渲染尾
   （`0x79a30`）和同一个 x 起点（216）。光看调用点分不开，所以引入
   **sticky 页**：一旦根据标签路径确定了当前页，同一段连续绘制里就沿用这个判断。
2. 真"配置按键"页有 24 行，其中 `A`/`B`/`X`/`Y` 是**厂商自己画的**，从来没走过
   我们的字符串表。这些行在表里用 `OFF_ANY (0xFFFF)` 标记，只能靠
   `(page, y)` 定位。

行表不是手写的，是跑厂商自己的主菜单构建器（`0x7F3E0`）然后**遍历它返回的菜单树**
反推出来的 —— 这样除非程序里根本没这个页面，否则不可能漏。见
`tools/gen_rowtab.py`。

### 200% 网格

菜单全部重画在 800×480 画布上，字符格 16 px（`CELL`），右边界 784。
原版用 8×8 字模、行距 8；补丁按 `y = 行序 × 36` 之类的页面基准重新排布，
并且把数值列**右对齐到固定列**（`vr1`），这样中文长度不同也不会串列。

### 色块（喜爱颜色）

固件页尾部画两笔：外框（白，16×8，`bl 0x88430` @ `0x799ec`）和色芯
（14×6，尾跳转 @ `0x79a24`）。

识别难点在于：外框的 x 是 `[x19+0x10] + 0x118`，而 `[x19+0x10]` 在**真机上是 88**、
在 Unicorn harness 里是 256 —— 早期版本按 `x == 536` 判断，在真机上**一次都没命中**，
所以怎么改都不生效。

最终判据改成：

- 外框：**LR == 0x799f0**（全程序只有这一个 `bl` 指向 `fill_rect`，指纹唯一）
- 色芯：形状 `(w,h,y) == (14,6,297)`

然后搬到喜爱颜色行的数值列右侧。全量静态枚举证实：**整个程序只有 3 处**
`bl` 指向 `fill_rect`，第三处是 160×160 的黑底，形状对不上，不会误伤。

## 8. 汉化字符串是怎么进去的

1555 字节的翻译表（135 条）追加在 payload 后面，固定在 `SEG_VA + 0x2000 = 0x152000`。

原版引用这些字符串用的是 `adrp/add` 成对取地址，或者 `.data.rel.ro` 里的
`R_AARCH64_RELATIVE` 重定位项。补丁分别处理：

- **80 处代码引用**：把 `add` 那一条改写成单条 `adr xD, 目标`
  （±1 MB 范围，`0x7xxxx`..`0x82xxx` 完全够）
- **78 处重定位项**：直接改 RELA 的 `addend`

> ⚠️ 只改 `add` 槽、不改 `adrp`：因为那个 `adrp` 的基址寄存器经常被多条 `add`
> 复用，把 `adrp` 改掉会连累邻居。

原版英文字符串**一个字节都不动**，别处（比如 `"r2.5.2.2"` 的子串引用）继续正常工作。

## 9. 空间预算

注入段总共 64 KB，实际只用了 9747 字节：

| 区域 | 起址 | 占用 |
|---|---|---|
| 代码 + 只读数据 | `0x150000` | 838 字节（槽 8192） |
| 翻译表 | `0x152000` | 1555 字节 |
| （余量） | | 到 `0x15d1f8` 为止 |

想加功能，先看 `patch.py` 打印的 `code+rodata slot used: N / 8192 B`。

## 10. 验证方法论

设备上跑一次成本很高，所以绝大部分验证在主机上完成：

**Unicorn harness**（`harness/`）把打过补丁的二进制加载进模拟器，直接调用厂商的
页面构建器和行渲染器，把每一次 `draw_text` / `fill_rect` 记录下来，再渲染成 PNG。
它能验证"画出什么"，有一个**根本局限**：它是把模块加载在 VA 0 的，某些依赖真实
映射基址的常量（比如上面那个 `[x19+0x10] = 88`）**它测不出来**。

**照片标定**是对 harness 的补充：拿真机照片，用已知字数的整行标签标定量出
"照片像素 / 逻辑像素"的比例，再反解出真机坐标。色块位置的最终定位就是这么做出来的。

**静态全量枚举**：用 capstone 扫描全程序找所有 `bl` 到目标函数的位置（记得开
`md.skipdata = True`，否则生成器会在数据段的非法指令处**静默中止**，给出假的
"0 命中"结果）。

## 11. 开发过程中的教训

| 踩过的坑 | 根因 | 对策 |
|---|---|---|
| 呼出菜单即崩 | payload 里的绝对指针在 VA 0 下"碰巧"合法，harness 测不出来 | 只允许数组与 PC 相对引用，禁止指针表 |
| 菜单遮挡 LOGO / 行不对齐 | 原版行距不能照搬，页面要按新格宽重排 | 行表由厂商菜单树反推，不手写 |
| 配置按键页字小、Unmapped 未翻译 | 漏了厂商自绘的 A/B/X/Y 行；两个同名页面互相串页 | OFF_ANY 标记 + sticky 页消歧 |
| 色块"改了但没生效" | 判据用了 harness 的假坐标（536 vs 真机 368），真机上从未命中 | 改用 LR 指纹 + 硬编码形状 (14,6,297) |
| 模拟器里全绿、真机不生效 | harness 把模块加载在 VA 0，依赖映射基址的常量测不出来 | 去真机量：`XO=88` 复现 + 照片标定反解坐标 |
